# Contributing

Thanks for looking at the code. This page covers setup, the checks to run before a pull request, and how to add a check.

## Setup

Node 20.18.1 or later is required.

```
npm ci
npm run build
node dist/cli.js --version
```

## Before a pull request

Run the same commands that CI runs:

```
npm run typecheck && npm run lint && npm run format:check && npm test
npm run coverage
npm run build
```

`npm run format` fixes formatting. Coverage has thresholds (90% lines, 90% functions and statements, 85% branches on `src/`, apart from `src/cli.ts` and `src/types.ts`) and the command fails when they are not met.

Two generated things are checked by tests:

- `docs/checks.md` is written from the check registry. After changing a check, run `npm run docs:checks`.
- The files in `examples/` are written from the bundled fixture site. After changing a report or a check that the fixture site trips, run `npm run examples` and commit the new files. The screenshot `examples/report.png` is not regenerated by that command.

## Tests never reach the internet

Every test runs against the fixture server on `127.0.0.1`, or against a context built in memory. `test/setup.ts` makes any request to another host throw, so a test that needs the network fails at once. Do not add a test that depends on a real site. Examples and fixtures use `example.com`, `example.org` or `*.example`.

## Adding a check

1. Pick the group file in `src/checks/`: `seo.ts`, `health.ts`, `performance.ts` or `accessibility.ts`.
2. Add one entry to that file's list. A check has:
   - `id`, in the form `GROUP-NAME-NNN`, for example `SEO-TITLE-001`. The prefix must match the group (`SEO`, `HEALTH`, `PERF`, `A11Y`) and ids are unique.
   - `severity`: `error`, `warning` or `info`.
   - `scope`: `page` or `site`.
   - `title`, `why` and `fix`: plain text. `why` is one or two sentences. `fix` is an instruction.
   - `heuristic`: `null`, or a sentence that gives the threshold and the reason for it. Describe a threshold as a rule of thumb.
   - `run`: a function that reads the crawl result and returns findings through `emit(url, detail, evidence)`. `url` is `null` for a finding about the whole site.
   - `applies`, optional: return `false` when the check cannot run, for example a sitemap check when no sitemap was fetched. The check is then reported as not applicable and not as passed.
3. Write the tests first. Add a positive test, where the check fires, and a negative test, where it stays quiet, to the matching `test/checks-*.test.ts`. The helpers in `test/helpers/context.ts` build a crawl result in a few lines.
4. Run `npm run docs:checks` so `docs/checks.md` includes the check.
5. Update the check counts in `README.md` and `CHANGELOG.md` when you add or remove a check. A test compares the README counts with the registry.
6. Run the commands under "Before a pull request".

## Writing rules

These apply to the docs, to text inside checks, to messages and to comments.

- No em dashes or en dashes. Use a comma, a colon or a new sentence.
- No exclamation marks.
- Short sentences, plain words.
- No claims about speed, accuracy or other tools, and no numbers that were not measured. State what the tests and the example run show.
- Do not name real people, businesses or sites. Use `example.com`.

A test checks the dash and exclamation rules in the README, the changelog and every file in `docs/`.

## Commits

One plain subject line, in the imperative: "Add a check for X". Keep unrelated changes in separate commits.
